## CONTRACT ADDENDUM (shared verbatim with the gateway prompt; the gateway implements it)
A. New endpoint POST /enroll/challenge. Auth: operator bearer. Body: {}.
   200: {"challenge":"<base64url, 32 random bytes, unpadded>","expiresAt":<epoch seconds>}.
   Single use, TTL 300 s.
B. POST /enroll and POST /enroll/rotate request bodies gain two required fields:
   "challenge" (the exact string returned by A) and "authTier" ("hardware_confirm" or
   "in_app_confirm"). The Android key-attestation challenge bytes are the base64url-DECODED
   challenge (32 raw bytes). Responses gain an optional "authTier" (the tier the gateway derived).
C. New error codes (standard {code,message} body): ENROLL_CHALLENGE_INVALID (400, unknown/expired/used),
   ENROLL_ATTESTATION_INVALID (400, bad chain/challenge/key mismatch/tier mismatch),
   AUTH_TIER_NOT_ALLOWED (403, tier not permitted in this environment).
D. The 10-field capability message and signature encoding are UNCHANGED. The tier is a property
   of the kid in the gateway registry, not of the wire (D-T1).

## 1. Problems this stage fixes (from the audit of Stage 4.1)
- EnrollDeviceUseCase creates the key with no attestation challenge. Without one, Android returns
  a self-signed certificate, so "chain not empty" proves nothing.
- The 4.1 key uses setUserAuthenticationRequired(true) only. BiometricPolicy allows DEVICE_CREDENTIAL,
  but that key cannot be unlocked by a PIN, and devices without biometrics must still work.
- BiometricGate.authenticate() returns Boolean, but the plan requires a CryptoObject bound to the
  signing key. KeystoreSigner's signatureProvider defaults to null, so signing is unreachable.
- VerifyBranchHeadUseCase returns Boolean, which cannot tell "drifted" from "could not check".

## 2. Design (follow exactly)
Tiers (new core/security/AuthTier.kt and AuthTierResolver.kt):
- hardware_confirm: Keystore-enforced per-use user authentication.
  API >= 30: authenticators BIOMETRIC_STRONG or DEVICE_CREDENTIAL (KeyguardManager.isDeviceSecure
  is enough; no biometric sensor needed).
  API 28-29: BIOMETRIC_STRONG only, and only if BiometricManager.canAuthenticate == SUCCESS.
  (The BIOMETRIC_STRONG|DEVICE_CREDENTIAL combination is not supported on API 28-29.)
- in_app_confirm: everything else, including no secure lock screen. The app never refuses to
  run or to read; it only degrades how writes are confirmed.
- AuthTierResolver.resolve(): pure function of injected facts (sdkInt, isDeviceSecure,
  biometricStatus) so JVM tests can cover every branch.

Key creation (DeviceKeySpec, DeviceKeyManager):
- hardware_confirm, API >= 30: setUserAuthenticationParameters(0, AUTH_BIOMETRIC_STRONG or
  AUTH_DEVICE_CREDENTIAL); API 28-29: setUserAuthenticationRequired(true). In both cases keep
  setInvalidatedByBiometricEnrollment(true) only when biometrics are the sole authenticator.
- in_app_confirm: setUserAuthenticationRequired(false), no invalidation flag.
- setAttestationChallenge(challengeBytes) is MANDATORY on every new key (enrolment and rotation).
- Existing key with a different tier than the resolver now returns, or created without a
  challenge: ensureDeviceKey must not silently reuse it. Surface a typed KeyNeedsRotation result
  so the UI offers rotation/re-enrolment. Never crash.
- Handle KeyPermanentlyInvalidatedException, UnrecoverableKeyException and a missing alias
  (lock screen removed, biometrics changed) as NEEDS_REENROLLMENT state. Reads keep working;
  writes are disabled with a clear message.

Enrolment: fetch challenge (A) -> generate fresh key with that challenge -> read chain -> require
chain size >= 2 (single self-signed cert = no attestation, refuse) -> send publicKey, chain,
challenge, authTier. Map ENROLL_CHALLENGE_INVALID by fetching a new challenge once, then surfacing
an error. Map AUTH_TIER_NOT_ALLOWED to a clear read-only state with explanatory text, not a crash.
Same for rotation.

Single path (the heart of 4.2). ConfirmAndMintCapabilityUseCase order: VerifyBranchHead ->
show summary (confirmation port) -> authorize signing -> mint. Details:
- hardware_confirm: build the Signature (SHA256withECDSA), initSign(privateKey) BEFORE the prompt,
  pass it in BiometricPrompt.CryptoObject, take result.cryptoObject.signature, and only then
  build the capability (timestamps, exp, nonce are computed AFTER the prompt so the TTL starts at
  approval), update(message), sign, convert DER to raw r||s via the existing EcdsaEncoding.
- in_app_confirm: show the same summary plus a typed confirmation of the first 7 hex chars of the
  expected head. No CryptoObject. The signer uses a non-auth key.
- Keep the wire message, codec and vectors byte-identical. Existing CapabilityMinterTest,
  codec vector tests and signer tests must pass UNCHANGED. If you cannot add the new flow without
  editing them, stop and report.
