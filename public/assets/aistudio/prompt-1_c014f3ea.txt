THE KEY (ADR 0013; read contract section 1.6 first)
- The journal and recovery key is a client-generated idempotency key: 128 random bits from SecureRandom, encoded as 32 lowercase hex characters (^[0-9a-f]{32}$). It is created when the operation intent is created, written to the journal BEFORE any send, and reused for repeated taps on the same intent.
- It is sent as JSON body field `idempotencyKey` on every write request. It is NOT part of the signed capability. Do not change the capability codec, the capability format or the conformance vectors.
- NEVER use, derive, hash or store the capability nonce, the signature or the capability string for any journal column, key, log or exception message (BD-3.2). The key is not a credential; it is still never logged together with anything secret.
- The console never resends automatically. A resend after an uncertain outcome is a new operation: new key, new capability, fresh operator confirmation.

TASKS
T3-201 Outcome model. Sealed type across the repository boundary with exactly: Succeeded | Refused | Conflict | Timeout | UncertainCompletion | RecoveryRequired. Carry only what the contract defines (auditRef, headSha, error code where the contract gives them). Success must never be representable from "request sent" alone (G-08).

T3-202 Journal.
- Room database (androidx.room 2.x). Entity: intent (operation, plan, task, branch, expected head, other non-secret request fields needed to identify the intent), idempotency key, state, created/updated timestamps, auditRef, last error code. Export schema JSON to app/schemas and commit it.
- Encryption: Keystore-wrapped AES-GCM field encryption using javax.crypto and the AndroidKeyStore provider. No new dependency. Fresh random IV per value, non-exportable key, fail closed on any key or decrypt error (the entry becomes RecoveryRequired; never a default or empty value). Keep the cipher behind an interface so JVM tests can substitute a fake.
- The intent is written BEFORE the send. If the journal write fails, nothing is sent.
- States must distinguish at least: intent recorded, sent, acknowledged, terminal outcome, uncertain, recovery required.

T3-203 Restart recovery.
- On app launch, entries in an uncertain state are resolved by GET /operations/{idempotencyKey}. WorkManager performs LOOKUPS ONLY. It never sends or resends a write.
- OperationRecoveryWorker obtains its dependencies through a Hilt EntryPoint (EntryPointAccessors). Do not use hilt-work or @HiltWorker (not on the build).
- Map lookup results to the outcome model EXACTLY as in contract section 4.3:
  * completed -> Succeeded, only after the live-head check (T3-302 rule: the live branch head must equal headSha); otherwise UncertainCompletion
  * pending -> UncertainCompletion
  * refused with code in {HEAD_DRIFT, HEAD_MOVED, NONCE_REPLAYED, SUBMISSION_IMMUTABLE, ANCESTRY_FAIL, RECONCILE_REQUIRED, IDEMPOTENCY_KEY_REUSED} -> Conflict
  * refused, any other code (including HALT_ACTIVE) -> Refused
  * failed -> RecoveryRequired
  * 404 OPERATION_NOT_FOUND -> RecoveryRequired (never an automatic resend, never treated as proof the request was not processed)
  * the lookup itself times out or the network is down -> the journal entry is left unchanged and retried later
  * Timeout is reserved for a WRITE SEND that received no response; it is always followed by a lookup
- Unknown status values or an unknown/missing code on failed/refused fail closed to RecoveryRequired.

T3-204 Idempotency. Repeated taps for the same intent reuse the same key and never create a second in-flight operation. A different intent gets a different key.
