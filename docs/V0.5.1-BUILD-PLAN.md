# operator-console — v0.5.1 Build Plan (Android Replacement of Termux CBridge)

Source: *Build Engine v0.5.1 — Android Replacement & Class B Gateway Readiness Assessment*.
Companion plan: `inscope-labs/build-engine` → `docs/release/V0.5.1-BUILD-PLAN.md` (owns Gateways B/C, conformance,
release machinery, and the cross-repository compatibility record).
Status: **DRAFT for operator review.**

This repository owns: the native Kotlin Android operator app (`app/`) and the **operator gateway (Gateway A)**
Cloudflare Worker (`gateway/`). Strategy: complete the app as a native Build Engine client; **do not** reproduce Termux
or execute `cbridge` shell scripts on Android. Preserve working code (Keystore, enrolment, capability signing, DTOs,
read layer); finish what is scaffolded.

## 1. Working rules

Standing AI Studio agent conventions apply to every Android stage:
- No release-build verification, no arbitrary shell setup commands, no HEAD drift-checks; drift failures go back to
  Claude for hash correction.
- Protected paths are **not** edited by the agent: `.github/workflows/*.yml`, `proguard-rules.pro`,
  `AndroidManifest.xml`, `app/build.gradle.kts`, `version.properties`, `build-logs/**`. Changes there are requested
  from Claude (examples: dependencies for Room/WorkManager, manifest permissions, CI expansion).
- Mandatory report per stage: `agent-reports/<UTC-ISO-timestamp>-<slug>.md`.
- AI Studio pushes its whole working tree and can silently overwrite out-of-band changes: before each stage, Claude
  rebases stacked branches; the operator reviews diffs. One writer per branch.
- Release APK assembly, signing and instrumented-test jobs are CI work owned by Claude/operator (OC-8), not the agent.
- Credentials: no GitHub PAT, repository token or signing material on the device or in the repo (ADR 0002). No secret
  in source, workflow files, fixtures or logs. Any token seen in chat is treated as exposed: revoke and replace.
- Never report a consequential operation as successful because a request was sent (see OC-4 outcome model).

## 4. Stages

### OC-0 — Contract and schema authority (docs, fixtures, tooling input)
- Reconcile `docs/gateway-contract.md`, `docs/capability-format.md` and `gateway/docs/*` with the Build Engine
  compatibility matrix and the three capability types (ctxop-v1 stays operator-action only).
- Publish canonical JSON schemas for the gateway API; add a DTO-conformance check that fails when Kotlin DTOs diverge
  from the schemas (item 40).
- Add the cbridge coverage matrix mirror (from build-engine BE-0), listing each command and the native use case.
- Acceptance: schemas committed; divergence check demonstrably fails on a deliberate mismatch; C-1…C-5 recorded as ADRs.

### OC-1 — Gateway A: make it real (items 35, 36, 37 partial; Gateway blocker P0)
- Commit `gateway/package-lock.json`; deterministic `npm ci`; remove every `|| true`; add typecheck step.
- Replace the 501 handler: routes (`doctor`, `sync`, `plans`, `tasks`, `decisions`, `status`, `admin`), operator bearer
  auth, device-signature verification, `ctxop-v1` verification (expiry, nonce single-use, exact SHA), guard set,
  audit log, Durable Object state, error catalogue.
- Fail closed on missing configuration, unavailable state, ambiguous policy.
- Acceptance: unit + conformance + log-hygiene all required and passing in CI; vector parity with Android; a test proves
  a replayed capability is refused and a stale branch head is a conflict.
- Owner: gateway code by agent or Claude; workflow files by Claude (protected).

### OC-2 — Configuration, transport security, preflight (items 4, 5; P1 pins)
- Validated environment configuration (test/staging/production) replacing `gateway.invalid`; Settings screen allows
  editing with validation (HTTPS only, hostname rules, no credentials in URL).
- Certificate pins (primary + backup), pin rotation procedure, and the C-1 posture (mTLS or documented alternative),
  server identity verification, device authentication, certificate rotation.
- Connectivity/preflight check: reachability, TLS identity, clock skew, contract-version compatibility, enrolment state.
- Acceptance: JVM tests for pin matching/rotation and config validation; preflight screen reports each check separately.

### OC-3 — Device enrolment and key lifecycle (item 2)
- Implement `EnrollDeviceUseCase`, `RotateDeviceKeyUseCase`, `ReportDevicePostureUseCase`, `DeviceEnrollmentStore`,
  `DeviceKeyManager`, `DeviceAttestation`, `StrongBoxSupport`: public-key registration, attestation, rotation,
  server-side enrolment records (gateway side in OC-1), and recovery after device replacement.
- Keys non-exportable; private key never leaves Keystore; attestation chain verified server-side.
- Acceptance: enrolment, rotation and replacement-recovery flows pass against the controlled test gateway.

### OC-4 — Privileged operations, confirmation, and durable recovery (items 1, 7, 8, 9, 32, 47)
- Implement `ConfirmAndMintCapabilityUseCase` as the **single path** to a capability: display exact task, plan, branch,
  expected SHA and scope → biometric (`BiometricGate`) → mint → send.
- Implement `OperationRepositoryImpl` and: `PublishTaskUseCase`, `UploadSubmissionUseCase`, `ReconcileUseCase`,
  `HaltUseCase`, `ResumeUseCase`, `DecideFrameworkUseCase`, `CreateWorkOrderUseCase`, `SetTaskStatusUseCase` (C-2),
  `VerifyBranchHeadUseCase`.
- Outcome model (item 7): `Succeeded`, `Refused`, `Conflict`, `Timeout`, `UncertainCompletion`, `RecoveryRequired`.
  Publication is only reported successful after gateway confirmation and head verification.
- Durable operation journal (C-4): record intent before sending; idempotency key + capability nonce; on restart,
  reconcile uncertain operations by querying the gateway rather than resending; repeated taps never duplicate a
  consequential operation; survive process death, network loss and background restrictions.
- Acceptance: JVM tests for every outcome and for crash-between-send-and-ack; no unresolved `TODO` in these classes.

### OC-5 — Operator interface (items 3, 6)
- Replace scaffold screens: dashboard and navigation; plan discovery/inspection; task selection and status; work-order
  creation; context-link generation; submission intake and inspection; publication and reconciliation; halt/resume;
  revocation and audit inspection; sync and diagnostics.
- Show data age and provenance for any cached read (item 33); disable state-changing actions when offline or stale.
- Acceptance: UI state tests for each screen; accessibility and small-screen layout checks on the A03 Core profile (item 60).

### OC-6 — Class B operator workflow (items 16, 17, 31, 44 console side, 45)
- Context-link generation against the read gateway contract (BE-4): choose exact files, bind to immutable commit and
  work order, issue links; list status, re-mint, revoke, fetch audit.
- Submission inspection and approval: file hashes, expected branch SHA, path restrictions, conflict reporting; transfer
  and publication remain explicit operator actions via OC-4.
- Revocation and audit workflow across Gateway A and the read/write gateways (contracts from BE-4 to BE-6).
- Acceptance: tests against the controlled gateway for tampered hash, moved head, path escape, revoked link.

### OC-7 — CBridge command coverage (items 27–30, 33)
- Native use cases for `doctor`, `sync`, `upload`, `publish`, `reconcile`, `halt`, `resume`, plus work-order and task
  management with safe status transitions and branch-head verification.
- Coverage matrix completed: every supported `cbridge` operation maps to a native feature or a documented alternative
  (C-3); README scope text updated to match.
- Acceptance: matrix has no empty row; each native feature has a named test.

### OC-8 — CI, release integrity, device and system acceptance (items 10, 38, 41, 43, 50; acceptance gate)
- CI (Claude/operator, protected files): JVM tests, instrumented tests, emulator workflow tests, release APK assembly,
  APK signing and artifact verification, dependency/vulnerability checks, **release check that rejects unresolved
  `TODO`, placeholder implementations, `gateway.invalid`, dummy URLs and unsupported operation paths**.
- APK published separately from the Build Engine archive with its own version, checksum, signing identity and upgrade
  instructions; safe install, upgrade and recovery process (item 34).
- Device test on Samsung Galaxy A03 Core (Android 13): process termination, background restrictions, biometrics,
  network recovery.
- Cross-system integration test: the real app against staging Gateway A, B and C (with build-engine BE-7).
- Termux retirement acceptance is recorded only after the whole BE-7 pilot passes.

### OC-9 — Incidental (items 52, 55, 56, 57, 58, 59, 60) — non-blocking
- Unified operation history, offline read cache, submission comparison viewer, native notifications, APK update
  notifications, structured diagnostic export (no credentials), accessibility polish. Do not delay OC-8.

## 6. Gates

- Gate 0: C-1…C-5 closed; schemas and DTO check in place.
- Gate 1: Gateway A passes CI and conformance with no permissive steps (end of OC-1).
- Gate 2: app works end-to-end against the controlled gateway for enrolment, mint, publish, reconcile, halt/resume (OC-2…OC-4).
- Gate 3: coverage matrix complete; no scaffold markers; release check green (OC-7, OC-8).
- Gate 4: A03 Core device acceptance plus staging integration; operator signs Termux retirement.

## 7. Risks

| Risk | Mitigation |
|---|---|
| AI Studio silent overwrite of out-of-band changes | Rebase before each stage; diff review; protected paths |
| Repeating a consequential operation after a crash | Journal-before-send, idempotency key, reconcile on restart |
| Empty pins/placeholder mTLS reaching production | Release check blocks; C-1 decision required |
| Gateway/app contract drift | Schema-validated DTOs (OC-0) in CI |
| Low-resource device behaviour | Early A03 Core runs, not only at OC-8 |
