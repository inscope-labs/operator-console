# Conformance Vectors Specification (`docs/fixtures/vectors/`)

This directory documents the format and schema of test conformance vectors for the `ctxop-v1`
capability codec, cryptographic signers, and signature transcoding routines.

> **CRITICAL**: Per Prerequisite P2, cryptographic signature vectors (`hmac_vectors.json`,
> `ecdsa_vectors.json`) must be generated by a verified reference script or standard cryptographic
> toolchain. They must never be manually synthesized or estimated by an AI agent.
>
> **All four JSON files are generated** by `generate_vectors.py` in this directory
> (`python3 docs/fixtures/vectors/generate_vectors.py`, needs `cryptography` >= 43). Output is
> deterministic (RFC 6979 ECDSA, fixed test key) and the script verifies every vector before writing.
> Do not edit the JSON by hand; change the script and regenerate. The keys and secrets in these
> files are public TEST values and authorise nothing.

## 2. File Schemas & Expectations

### 2.1 `valid_capabilities.json`
Contains canonical test cases of valid capabilities covering all allowed operations (`PUBLISH`, `HALT`,
`RESUME`, `UPLOAD`, `RECONCILE`, `DECIDE`, etc.), exercising both task-scoped branches (`task-*`)
and engine-scoped branches (`engine`).

**Schema:**
```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "vectors": [
    {
      "id": "valid-publish-minimal",
      "description": "Valid publish capability for task-10008",
      "fields": {
        "domain": "ctxop-v1",
        "kid": "k2",
        "exp": 1761840000,
        "order": "order-7731",
        "plan": "atlas",
        "task": "10008",
        "op": "PUBLISH",
        "branch": "task-10008-refactor-parser",
        "head": "9f2c1b7e4a5d6038c1b2a9e7d4f6081c3b5a7e9d",
        "nonce": "7f3c9b1e5d2a7046"
      },
      "canonicalMessage": "ctxop-v1\nk2\n1761840000\norder-7731\natlas\n10008\nPUBLISH\ntask-10008-refactor-parser\n9f2c1b7e4a5d6038c1b2a9e7d4f6081c3b5a7e9d\n7f3c9b1e5d2a7046"
    }
  ]
}
```

### 2.2 `codec_mutations.json`
Vectors designed to verify that the decoder is **strictly fail-closed**. The test harness asserts
that attempting to decode these inputs results in a parsing error and maps to the specified rejection code.

**Expected Mutation Classes:**
- `extra-field`: 11 lines instead of 10 (`BAD_FIELD_COUNT`).
- `missing-field`: 9 lines instead of 10 (`BAD_FIELD_COUNT`).
- `crlf-line-endings`: Contains `\r\n` (`BAD_ENCODING`).
- `trailing-line-feed`: Contains a trailing `\n` at the end (`BAD_ENCODING`).
- `invalid-domain-separator`: Domain literal is not `ctxop-v1`.
- `unknown-operation`: Operation string not in `OperationType` (`UNKNOWN_OP`).
- `invalid-kid-regex`: Key selector contains invalid characters (spaces, punctuation).
- `negative-exp`: Expiry is negative or non-numeric.
- `branch-not-task`: Task-scoped operation specifying non-task branch (e.g. `main`) (`BRANCH_NOT_TASK`).
- `malformed-head-sha`: SHA is not exactly 40 lowercase hexadecimal characters.
- `short-nonce`: Nonce is not 16-64 lowercase hex characters (short, uppercase or overlong).
- `noncanonical-exp`: `exp` with a `+` sign, leading zeros, or overflowing a `Long`.
- `engine-op-task-branch`: Engine-scoped operation carrying a `task-*` branch (`BRANCH_MISMATCH`).
- `unsafe-engine-branch`: Engine branch containing `..` or starting with `-`.
- `empty-field`: A required field is empty.

Every mutation vector must be rejected by the Android decoder (`IllegalArgumentException`); the
`expectedErrorCode` is the code the **gateway** must answer with.

**Schema:**
```json
{
  "vectors": [
    {
      "id": "mutation-extra-field",
      "rawMessage": "ctxop-v1\nk2\n1761840000\norder-7731\natlas\n10008\nPUBLISH\ntask-1\n9f2c1b7e4a5d6038c1b2a9e7d4f6081c3b5a7e9d\n7f3c9b1e5d2a7046\nextra_field",
      "expectedErrorCode": "BAD_FIELD_COUNT"
    }
  ]
}
```

### 2.3 `hmac_vectors.json`
Vectors for testing `HmacCapabilitySigner` and `CapabilityMinter`.

**Schema:**
```json
{
  "vectors": [
    {
      "id": "hmac-sha256-publish",
      "secretUtf8": "lab-secret-key-32-chars-minimum!!",
      "message": "ctxop-v1\nk2\n1761840000\norder-7731\natlas\n10008\nPUBLISH\ntask-10008-refactor-parser\n9f2c1b7e4a5d6038c1b2a9e7d4f6081c3b5a7e9d\n7f3c9b1e5d2a7046",
      "expectedSignatureBase64Url": "tql0gx__AYfVQxd_EbSYo7PUCC9CwkITVr6cUoGKs2k"
    }
  ]
}
```

### 2.4 `ecdsa_vectors.json`
Vectors for verifying ECDSA P-256 signature verification and ASN.1 DER ↔ raw IEEE P1363 transcoding.

Must include:
1. Standard DER to IEEE P1363 test pairs.
2. High-bit edge cases:
   - `r` or `s` with high bit set (causing ASN.1 DER to prepend `0x00`).
   - `r` or `s` shorter than 32 bytes (requiring zero-prefix padding in raw 64-byte P1363 representation).

The file has a top-level `publicKeyJwk` (the TEST key every vector was signed with) and a `vectors`
array. Each vector has a `kind`:

| `kind` | Fields | Assertion |
|---|---|---|
| `derToRaw` | `message`, `derSignatureBase64`, `expectedRawP1363Base64Url` | DER -> raw gives exactly the expected 64 bytes, and raw -> DER gives back the DER. Covers `r`/`s` with the high bit set (DER `0x00` pad), `r`/`s` shorter than 32 bytes with and without a DER pad, both high, and a typical case. |
| `verify` | `message`, `expectedRawP1363Base64Url`, `verifiesUnderPublicKey` | Verification under `publicKeyJwk` gives exactly this result (includes tampered signature and tampered message, which must NOT verify). |
| `malformedDer` | `derSignatureBase64`, `expectedError` | DER -> raw must reject (`INVALID_DER`): truncated, wrong tags, trailing bytes, empty. |
| `rawWrongLength` | `rawBase64Url`, `expectedError` | A raw signature that is not exactly 64 bytes must be rejected (`INVALID_RAW_LENGTH`). |

`derSignatureBase64` is standard base64 with padding (as a DER blob); every `*Base64Url` field is
base64url without padding.

## 3. Usage in Test Suites

The test files in `app/src/test/kotlin/` consume these vectors during JVM execution:
- `OperatorCapabilityCodecVectorsTest`: Iterates through `valid_capabilities.json` and `codec_mutations.json` (implemented; shares `testutil/VectorLoader`).
- `CapabilitySignerTest`: Asserts HMAC signatures against `hmac_vectors.json` and transcoding against `ecdsa_vectors.json`.
- `CapabilityMinterTest`: Verifies that combining the codec with signers yields bit-for-bit matches against vectors.
