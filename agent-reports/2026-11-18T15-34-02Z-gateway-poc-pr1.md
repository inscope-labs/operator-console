## 1. What changed

### 1.1 The decoder (`gateway/src/capability/codec.ts`)

`decodeCapability` previously accepted a large class of malformed capabilities. It now enforces `docs/capability-format.md` field by field and refuses each fault with the catalogue code that names it.

| Field | Before | Now | Code on refusal |
|---|---|---|---|
| framing | CR refused; a leading/trailing LF produced a field-count error | a leading or trailing LF is refused as an encoding fault before the field count is taken | `BAD_ENCODING` |
| `kid` | `^[A-Za-z0-9_]{1,16}$` | unchanged | `BAD_ENCODING` |
| `exp` | `Number(expRaw)` — accepted `+1761840000`, `01761840000` and values beyond a `Long` | canonical decimal only (`^(0\|[1-9][0-9]*)$`), greater than zero, and it must fit a signed 64-bit integer | `BAD_ENCODING` |
| `order`, `plan`, `task` | not checked | required, not empty | `BAD_ENCODING` |
| `nonce` | "not empty" only | `^[0-9a-f]{16,64}$` | `BAD_ENCODING` |
| `op` | closed set | unchanged | `UNKNOWN_OP` |
| `branch` | `branch !== 'engine' && !/^task-…/` → `BRANCH_INVALID` | per-operation scope (see §1.2) | `BRANCH_NOT_TASK` / `BRANCH_MISMATCH` / `BAD_ENCODING` |
| `head` | `/^[0-9a-f]{40}$/i` — accepted upper case | `^[0-9a-f]{40}$` — lower case only | `BAD_ENCODING` |

Field checks follow the order of `docs/gateway-contract.md` §7 (kid, exp, nonce, op, branch, head) so the code a caller sees matches the contract's own ordering.

**`exp` and the 64-bit range.** The raw field is checked as *text* first (`EXP_CANONICAL_RE`) and then as a `BigInt` against `9223372036854775807n`, because `Number()` alone accepts `+1761840000`, `01761840000` and `99999999999999999999`. The decoded value is stored as a `number`: above 2^53-1 the exact integer is not representable, so the capability keeps the nearest representable value. That is the documented exception the brief allows for `valid-exp-max-long`.

### 1.2 Branch scope

`docs/capability-format.md` §2 (`branch` row) splits the operations into two scope classes:

- **Task-scoped** — `PUBLISH`, `UPLOAD`, `RECONCILE`, `DECIDE`, `ORDER`, `SET_IN_PROGRESS`, `SET_DONE`: the branch must match `^task-[A-Za-z0-9._-]+$`. `main` and `engine` are refused with **`BRANCH_NOT_TASK`**.
- **Engine-scoped** — `HALT`, `RESUME`, `SYNC`, `DOCTOR`, `NEW_PLAN`: the branch must **not** be a `task-*` branch — refused with **`BRANCH_MISMATCH`** — and must be a safe branch name.

A safe engine branch name is refused with `BAD_ENCODING` when it contains `..`, starts with `-` or `/`, ends with `/`, `.` or `.lock`, contains `//` or `@{`, or carries a space, a control character or one of the characters git refuses in a ref name (`~ ^ : ? * [ \`).

**Where the configured engine branch is decided.** Equality with the *configured* engine branch (`engine`) is **not** a decoder decision — the value is configuration, not wire format. It is enforced where the configuration is available:

- `gateway/src/routes/halt.ts` — `cap.branch !== 'engine'` → `BRANCH_INVALID`; the body branch must also be `engine` → `BRANCH_MISMATCH`.

The decoder therefore accepts a well-formed engine branch that is not the configured one — that is exactly what the **valid** vector `valid-engine-branch-with-slash` (`SYNC` on `release/1.0`) requires. The conformance suite asserts that vector decodes; the route is where it is finally refused. **Every one of the 30 mutation vectors is decided by the decoder** — no vector had to be moved out of it.

### 1.3 The error catalogue

`BRANCH_NOT_TASK` was missing from `gateway/src/errors/catalogue.ts`. It is added — **one code, no other** — because `docs/gateway-contract.md` §4.1 lists it:

> `BRANCH_NOT_TASK` / `BRANCH_INVALID` | `400 Bad Request` | Scope | Task operation branch does not match required regex `^task-[A-Za-z0-9._-]+$` or is `main`.

`BRANCH_NOT_TASK` → `400`, message *"Task-scoped operation must carry a task-* branch, not main or the engine branch"*. `gateway/docs/error-catalogue.md` carries the same row.

`BRANCH_INVALID` is **not** removed: it is still produced by the guard layer (`src/guards/g3-branch-shape.ts`), by `src/routes/branches.ts` and by the halt route's own engine-branch check.

### 1.4 The error-code plumbing

| File | Change |
|---|---|
| `src/capability/verify.ts` | `VerifyFailure` gains `BRANCH_NOT_TASK`; the decoder's `BRANCH_NOT_TASK` and `BRANCH_MISMATCH` are mapped instead of falling through to `BAD_ENCODING`. |
| `src/capability/gate.ts` | `codeMap` gains `BRANCH_NOT_TASK`. |
| `src/idempotency/write-gate.ts` | `BRANCH_NOT_TASK` is in the *refused* set, so the operation record shows a refusal, not a failure. |

### 1.5 The conformance test

`gateway/tests/conformance/v-capability-vectors.test.ts` now asserts **the code each vector names** — the "codec currently emits BRANCH_INVALID" allowance and every other loose allowance (`expect(msg.length).toBeGreaterThan(0)`) are gone. The assertion is on the thrown `Error.message`, not on `String(error)`.

`valid-exp-max-long` now asserts that the decode **succeeds** and that `exp >= Number.MAX_SAFE_INTEGER`; an exact round-trip above 2^53-1 is not required and is not claimed.

## 4. Signature verification — confirmed

**Verification uses the received message string, not a re-encode.** In `gateway/src/capability/verify.ts`:

1. `splitSignedCapability(raw)` splits the raw value at the last LF into `message` and `signature`.
2. `decodeCapability(message)` decodes **that** message.
3. `verifySignature(message, signature, key)` verifies the signature over `new TextEncoder().encode(message)` — the bytes as received.
4. The returned `signed.message` is the received message, and it is what reaches the audit path.

`encodeCapability` is **never called anywhere in `gateway/src/`** (grep: one definition, no call site). The gateway only decodes. This matters more now: with `exp` above 2^53-1 no longer round-tripping exactly, a re-encode-based verification would have been unsound — it is not used.

## 6. Deviations, judgement calls and open questions

### 6.1 `SET` is a contract silence — implemented as task-scoped

`docs/capability-format.md` §2 lists the task-scoped ops as `PUBLISH, UPLOAD, RECONCILE, DECIDE, ORDER, SET_IN_PROGRESS, SET_DONE` and the engine-scoped ops as `HALT, RESUME, SYNC, DOCTOR, NEW_PLAN`. **`SET` is in neither group**, although `SET` is in the `OperationType` enumeration and the gateway's closed wire set. The contract is silent, so this is recorded rather than chosen silently: `SET` is implemented as **task-scoped** (it is a task status operation, the sibling of `SET_IN_PROGRESS` / `SET_DONE`).

*Effect:* a `SET` capability on a non-`task-*` branch is refused `BRANCH_NOT_TASK` at decode time. A well-formed `SET` capability still decodes and is refused later by the route as a reserved operation (`400 BAD_ENCODING`, contract §3.17). **Open question for the operator:** should `SET` be listed in `docs/capability-format.md` §2, and in which scope group?

### 6.2 `BRANCH_NOT_TASK` replaces `BRANCH_INVALID` at decode time

For a task-scoped op on `main` or `engine`, the decoder now says `BRANCH_NOT_TASK` where it previously said `BRANCH_INVALID`. Both codes are listed by contract §4.1 for the same condition; the vectors name `BRANCH_NOT_TASK`, and the brief says to use the vector's code. `BRANCH_INVALID` remains in the catalogue for the guard layer and the routes.

### 6.3 The `exp` boundary

`exp` must be greater than zero. `0` is refused (`mutation-zero-exp` → `BAD_ENCODING`), matching the pre-existing behaviour and the vector. A negative `exp` is refused by the canonical-decimal rule before the sign is ever considered.

### 6.4 Two existing unit tests changed *meaning*, not just fixtures

1. **`tests/unit/routes/halt.test.ts` — "rejects non-engine branch on halt".** The old case sent a `HALT` capability on `task-x` and expected `400 BRANCH_INVALID` from the route. An engine-scoped op carrying a `task-*` branch is now refused **in the decoder** with `BRANCH_MISMATCH` (`403`), before the route runs — the code the vector names. The case was rewritten to assert `403 BRANCH_MISMATCH`, and a **second** case was added with the branch `main` (a well-formed branch that is neither `engine` nor `task-*`), which still reaches the route and still asserts `400 BRANCH_INVALID`. The route's own check keeps its coverage.
2. **`tests/unit/capability/edge-cases.test.ts` and `verify.test.ts`** — the "wrong branch pattern" cases were renamed to `BRANCH_NOT_TASK` and now assert that code.

Every other change to an existing test is a **fixture** change: the old fixtures used non-hex nonces (`'nonce-abc'`, `'nonce-1'`, `'n-reg-1'`, `'nonce-' + uuid.slice(0,8)`), which the contract has never allowed. They are now 16 lower-case hex characters. `tests/unit/routes/decide.test.ts` asserted `expect(written[0]).not.toContain('nonce-')`; with the old prefix gone that assertion would have been vacuous, so it now asserts that the **actual nonce** of the minted capability is absent from the persisted record.

### 6.5 Four conformance files are empty placeholders — they fail as suites

`v1-ruleset-main.test.ts`, `v5-capability-scope.test.ts`, `v9-adapter-privacy.test.ts` and `v10-transaction-idempotency.test.ts` contain only a comment. vitest reports a file with no test suite as a **failed suite**, so `npm run test:conformance` could not be green while they were in place, whatever the codec did. Each now carries one `it.todo` describing the case, so the file is a runnable suite and the gap is visible as `4 todo` in the report instead of a failure. **No conformance assertion was added, removed or weakened**, and no expectation was invented for V1/V5/V9/V10 — the brief places implementing them out of scope, and their requirements are not derivable from the contract without inventing them.

### 6.6 Not done, deliberately

- The conformance suite is now run in CI, but the **deploy gate** is not — the brief allows exactly one workflow line, and adding a deploy gate is a second.
- `docs/capability-format.md` was **not** edited to document `SET`'s scope (§6.1) or to add the engine-branch safety rule. The brief scopes PR 1 to `gateway/**`; the authority document is the operator's to amend.
- `src/routes/halt.ts` still answers `BRANCH_INVALID` for a capability branch that is neither `engine` nor a task branch. It is a route-level scope check, not a decoder one, and the brief did not ask for it to change.

## 7. Open questions for the operator

1. **`SET` scope** — which scope group does `SET` belong to in `docs/capability-format.md` §2? Implemented as task-scoped (§6.1).
2. **`BRANCH_INVALID` vs `BRANCH_NOT_TASK`** — should the decoder use one code for both, as it does now (`BRANCH_NOT_TASK`), or keep `BRANCH_INVALID` for the general "does not match `^task-…$`" case and reserve `BRANCH_NOT_TASK` for `main`/`engine`? The vectors only pin `main` and `engine`.
3. **The configured engine branch is hard-coded** as `'engine'` in `src/routes/halt.ts`. Should it be configuration (`REPOS`/env), as `docs/capability-format.md` §2 says ("the *configured* engine branch")?
4. **Conformance cases V1, V5, V9, V10** remain unimplemented and now report as `todo`. They need a specification before they can be written.
5. The `valid-engine-branch-with-slash` vector shows the engine branch is not fixed at `engine` in the vector set. If the engine branch is to become configurable, the vector set needs a generator update (`docs/fixtures/vectors/generate_vectors.py`) — **not** a hand edit of the JSON.
