## 1. What this stage changed

`POST /tasks/:id/publish` was the gateway's false-success defect called out in
RELEASE-PLAN A.4 (defect 1) and GATEWAY-A-COMPLETION-PLAN Stage 1.1. It ran the
capability gate and the core guard set and then answered:

```
HTTP 200
{ "ok": true, "phase": 1, "message": "capability + nonce + core guards passed — publish transaction not yet implemented" }
```

A client that trusted the status code reported a publication that never
happened. It now answers:

```
HTTP 501
{ "error": "NOT_IMPLEMENTED",
  "message": "Publish is not implemented in this gateway build; no branch was published",
  "request_id": "<uuid>" }
```

The handler was reduced to that single refusal. Everything that could have
looked like progress or success was removed: the `ok: true` body, the
`phase: 1` marker, the `branch`/`head` echo and the "guards passed" message.

### Design decisions

1. **The refusal happens at the capability boundary, before the request is
   interpreted.** The body is not parsed, the capability is not verified, the
   nonce is **not** consumed, no GitHub adapter is constructed and no repository
   state is read or written. Consuming a single-use, biometric-confirmed
   capability on a call that cannot run would force the operator to re-confirm
   for nothing; the minted capability stays unspent and usable when Stage 3.2
   lands.
2. **The operator-token and configuration gates still run.** The router rejects
   a missing/invalid `OPERATOR_TOKEN` (401 `OPERATOR_AUTH`) and invalid config
   (503 `CONFIG_INVALID`) before the handler is reached, so the stub is not an
   open surface. Both are asserted by tests.
3. **The code is a catalogue code, not an ad-hoc string.** `NOT_IMPLEMENTED`
   was added to `src/errors/catalogue.ts` with HTTP status 501 and to
   `gateway/docs/error-catalogue.md`, and recorded in ADR 0002. This satisfies
   T1-103 ("return 501 `NOT_IMPLEMENTED` through the error catalogue") and keeps
   the catalogue and the TypeScript union identical ahead of the Stage 1.3
   freeze.
4. **The response body never claims success.** No `ok`, no `accepted`, no
   `auditRef`, no `operation`, and the message contains no success wording and
   no caller-controlled input.
5. **The success shape of the contract is untouched.** `docs/gateway-contract.md`
   §3.8 still describes the real `200 {accepted, operation, branch, headSha,
   auditRef}`; only the gateway's current behaviour was corrected. Stage 3.2
   implements the contract shape.

### Tests added

`gateway/tests/unit/routes/publish-stub.test.ts` — 7 cases:

1. answers `501 NOT_IMPLEMENTED` and never 2xx (`res.ok === false`);
2. the body never claims success (no `ok`, no `accepted`, no `auditRef`, no
   `operation`, no `"accepted"` anywhere in the raw payload);
3. still answers `501` when the body is missing or malformed;
4. **does not consume a capability nonce** — the test injects a
   `NONCE_STORE` namespace that records and rejects every access; the recorded
   call list must be empty;
5. still requires the operator token (401 `OPERATOR_AUTH`);
6. still fails closed on invalid configuration (503 `CONFIG_INVALID`);
7. is registered as an operator-token-protected privileged route
   (`requiresOperatorToken`, `requiresCapability`).

Case 4 is the one that matters most for the "no side effects" claim: the
handler must be unreachable to the nonce store. The test env also carries empty
GitHub App credentials, so any attempt to build an adapter would surface as
`NETWORK` instead of the `501` under test.

1. **Stage 1.4 (CI hardening) — required human workflow change.** `.github/workflows/cbridge-ci.yml`
   must drop every `|| true`, require `npm ci`, `tsc --noEmit`, `vitest run`,
   `verify-log-hygiene` and `check-repo-privacy`, and be renamed `gateway-ci.yml`
   (the deploy workflow is `cbridge-deploy.yml`). Per R-09 the agent reports the
   change and stops; the human applies it. The workflow must also stop pointing
   `setup-node`'s `cache-dependency-path` at a file that is not in the repository
   until that file is committed.
2. **Stage 1.4 — commit `gateway/package-lock.json`.** It is generated here
   (`npm install`) but deliberately **not committed**, because Stage 1.4 owns the
   lockfile and committing it from this stage could collide with that work. It is
   the current first blocker for the CI job (§4): `setup-node` fails without it,
   so `npm ci` and every later step are skipped.
3. **Stage 1.4 — the 5 `TS6133` errors must be cleared before `tsc --noEmit`
   can be a hard gate** (RELEASE-PLAN T1-104). They are outside this stage's paths.
4. **Stage 1.2 — `tests/unit/routes/config-gate.test.ts` must be updated.** It
   currently asserts that `ENVIRONMENT=staging` is invalid; Stage 1.2 makes
   staging a valid environment, so that assertion inverts.
5. **`.gitignore` does not ignore `node_modules/`.** `gateway/node_modules/` and
   `gateway/package-lock.json` show as untracked, and the G-02 convention is
   "the agent pushes its whole working tree". A `node_modules/` line should be
   added before the next agent runs `git add -A`. Not changed here — `.gitignore`
   is outside this stage's path list.
6. **Contract drift noted, not acted on.** `docs/gateway-contract.md` §4 specifies
   the error body as `{ "code", "message" }` while the gateway emits
   `{ "error", "message", "request_id" }`. That drift is assigned to RELEASE-PLAN
   T1-201 ("align the gateway to the contract") / GATEWAY Stage 1.3. The gateway
   keeps its existing body shape so that no other route or test changes shape in
   this stage; the new `NOT_IMPLEMENTED` refusal uses the same shape as every
   other gateway error.
7. **The other unimplemented surfaces** (`sync`, `doctor`, `admin`, `decisions`)
   are not routed at all today, so the router answers `502 NETWORK` from its
   "no route" fallthrough. T1-103 in RELEASE-PLAN also names them; converting
   them to `501 NOT_IMPLEMENTED` belongs to the stages that own those routes
   (3.6, 4.2, 4.3) — this stage touched only the publish handler, per its path list.

## 7. Operator-facing effect

The console (`app/`) already treats every non-2xx gateway response as
`REFUSED` and raises `GatewayHttpException` with the body
(`GatewayHttpClient.kt:65-77`); `ErrorMapper` maps the body to a failure state.
So the console can no longer display a publication that did not happen — it now
shows a refusal. No console-side change was needed for this stage, and none was
made.

The publish stub no longer reports success: `POST /tasks/:id/publish` answers

the stage introduces no regression against the `main` baseline (97 → 104 passing
tests, identical pre-existing failures and identical pre-existing type errors).
