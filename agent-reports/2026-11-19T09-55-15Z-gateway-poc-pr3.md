## 1. What changed

Contract §3.6: every item of `GET /tasks/next` carries a **required non-empty `order`** — the work-order identifier the task was issued under — and *"A task for which the gateway holds no work-order identifier is not listed as ready."*

Neither `PlanTaskRecord` nor `/tasks/next` carried the field, so the console had no identifier to copy into the capability's `order` field and could not mint a capability at all.

### 1.1 `gateway/src/durable-objects/plan-do.ts`

- `PlanTaskRecord` gains `order?: string` — the work-order identifier the task was issued under. The gateway reports the value it holds; it never derives, defaults or invents one.
- `/tasks/next` now **skips a ready task whose `order` is missing or empty**, and emits `order` on the items it does list.

### 1.2 `gateway/src/plan/client.ts`

The in-memory `/tasks/next` fallback (used by tests and single-isolate runs) does the same, with the **same control flow and the same skip rule** as the Durable Object, so the two paths cannot drift. A test asserts they agree byte for byte (§3).

### 1.3 `PUT /plans/:id` stores the order per task

No change was needed: the route passes the request body through to `putPlanRecord`, and both plan stores keep the `tasks` array verbatim, so an `order` on a task is stored as held. A test now pins that end to end — the local PoC harness seeds plans through this route (ADR 0016 D-2), so this is the path that matters.

### 1.4 The item's shape

The item now carries exactly the keys of `tasks-next.schema.json`: `id`, `planId`, `title`, `branch`, `status`, `headSha`, `order` — the schema's `required` list, with `additionalProperties: false`.

## 2. Why the skip rule matters more than it looks

The console's `TaskSummaryDto` (`app/.../core/network/dto/TaskSummaryDto.kt`) declares `order` **without a default** and fails closed in its `init` block:

```kotlin
val order: String,
) {
    init {
        require(order.isNotBlank()) {
            "TaskSummaryDto.order must be non-blank (docs/gateway-contract.md §3.6)"
        }
    }
}
```

An item without an `order` therefore **throws during deserialization** of the whole `/tasks/next` response — not just that one task. Had the gateway listed a task it holds no work-order identifier for, the console would fail to parse the list, not merely skip one entry. The skip rule is what keeps the response parseable.

## 5. Deviations, judgement calls and open questions

### 5.1 One existing test fixture had to change

`tests/unit/routes/plans-read.test.ts` — *"GET /tasks/next returns ready tasks"* — seeded a task with **no** `order` and asserted that it was listed. Under §3.6 that task is not publishable and must not be listed, so the fixture now carries `order: 'order-7731'` and the test also asserts the value. This is a **behaviour change the contract requires**, not a test weakened to fit the code: the new file above pins the omission rule explicitly, so both directions are covered.

The Durable Object's equivalent case was updated the same way, and extended to assert the order.

### 5.2 The order is never generated — nothing was defaulted

No fallback value, no derivation from the plan id or the task id, no `order: t.order ?? ''`. A task without one is simply not listed, and the report says only what is held. This matches the contract's *"the gateway reports the value it holds for the task"* and the console's own rule (*"never invents one"*).

### 5.3 A pre-existing schema gap was left alone (reported, not fixed)

`tasks-next.schema.json` requires `branch` and `headSha` on every item, but a task record may hold neither, and `JSON.stringify` drops an `undefined` value — so such an item would violate the schema. This is **pre-existing** and outside this brief's scope (which is the `order` field), and the obvious fix — emitting `''` — would be inventing a value, which this brief forbids. The console tolerates it: `TaskSummaryDto.branch` and `.headSha` default to `""` and carry no non-blank requirement (only `order` does). **Reported for the operator.** A clean fix would be to skip such a task as well, or to amend the schema.

### 5.4 `order` is stored, not validated

`PUT /plans/:id` accepts whatever `order` string the caller supplies and stores it as held — there is no format rule for a work-order identifier anywhere in the contract, so none was invented. The only rule the contract states is **non-empty**, and it is enforced at the listing boundary (a task whose `order` is empty is not listed). An `order` of whitespace (`" "`) is non-empty and is listed as held.

### 5.5 Open questions for the operator

1. **The `order` of a task that is not ready.** A task with an order but a status other than `ready`/`unassigned` is not listed (unchanged behaviour) — the order is not consumed or reserved by listing it. Is a work order *issued* at the moment the task becomes ready, or earlier? The gateway does not model work orders (BD-1.3 option B), so it only reports what it is given.
2. **Where the order comes from.** The gateway holds it because `PUT /plans/:id` was told it. The engine tooling that creates work orders (BD-1.3 option B) is out of this repo. The local PoC harness seeds it by hand.
3. **The `branch`/`headSha` schema gap** (§5.3).
4. **`PUT /plans/:id` still bypasses the capability-gated transition** — reported in PR 2 (#93) and unchanged here.

```

FAILED — stale allowlist entry: C1 app/.../ui/device/DeviceManagementScreen.kt no longer matches anything
```

`b5ed919` gave those three screens their ViewModels, which **removed the `TODO(Stage 4.4 / T4-401)` scaffold markers** the allowlist entries were written to match. The gate treats a stale allowlist entry as a failure by design — *"an allowlist entry that no longer matches anything is itself a failure, so the list cannot rot"* — which is exactly what happened.

**This PR is not the cause.** It touches `gateway/**` and this report only, and `Gateway CI` is green on its head. `android-ci` has **no `paths` filter on `pull_request`**, so it runs for gateway-only PRs and inherits `main`'s red.

**The fix is app-side and outside this brief's scope** (this brief allows edits to `gateway/**` and the agent report only): delete those three entries from `_entries()` in `scripts/release-check.py` — the markers they allowlisted no longer exist, so the findings they were tracking are closed.
