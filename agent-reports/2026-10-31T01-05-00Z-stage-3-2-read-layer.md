## Tasks Completed

- **T3-201 (`domain/model/*` — the read models)**:
  - `Plan`: implemented, with `completedTaskCount` and the gateway's `status` carried as it arrives.
  - `PlanStatus`, `PlanValidation`, `RenderCheck`: added to `Plan.kt` as the structured shapes of contract §3.3, §3.4 and §3.5. The validation's errors/warnings and the render check's issues are carried rather than reduced to a boolean — "invalid" without the reasons gives the operator nothing to act on.
  - `Task`: implemented, with the branch and head SHA travelling with it (design review §5 — the decision is about a specific branch at a specific SHA).
  - `TaskStatus`: implemented, with `UNKNOWN` added. The gateway's task vocabulary is its own; a status the console does not recognise is a task it cannot honestly summarise, and guessing whether work has started is the one guess the console must not make.
  - `TaskBranch`: implemented, with `guardsPassed` changed from `Boolean = false` to `Boolean? = null`. The console evaluates no guards and no read endpoint reports their outcome, so `false` would be a claim about the gateway's verdict that the console has no basis for.
- **T3-202 (`domain/repository/*`)**:
  - `PlanRepository`: implemented with `getPlans`, `getPlan`, `getStatus`, `validate`, `renderCheck`, all answering `AppResult`.
  - `TaskRepository`: implemented with `getNextTasks`, `getTask`, `branchFor`, `setStatus`, all answering `AppResult`.
  - `getStatus` is new: the contract defines `GET /plans/{id}/status` and the gateway API already carries it, but the scaffolded interface had no way to reach it.
- **T3-203 (`data/repository/*`)**:
  - `GatewayCalls.kt` (added): the shared `callGateway` helper that turns the transport's exceptions into the failure the domain sees, using the `ErrorMapper` — so a refusal carries the same state code wherever it is observed.
  - `PlanRepositoryImpl`, `TaskRepositoryImpl`: implemented. The DTO→domain mapping is mechanical and total; the gateway's vocabulary is carried across rather than reinterpreted.
  - `NotFoundException` → the `not_found` state, for a resource the gateway does not have — neither a refusal nor a protocol failure.
  - `branchFor` takes the head from the branch endpoint rather than from the task list, because the list's SHA is a snapshot and a capability is minted against the live head (docs/threat-model.md, V7).
- **T3-204 (`domain/usecase/read/*`)**: `GetPlansUseCase`, `GetNextTasksUseCase`, `GetStatusUseCase`, `ValidatePlanUseCase`, `RenderCheckUseCase` — implemented, thin on purpose: the seam the UI depends on, so a screen never learns that plans arrive as JSON over HTTP.
- Removed all `SCAFFOLD PLACEHOLDER` markers and `TODO`s from the files this stage owns.

## Deviations from the scaffold, and why

| The scaffold said | Now | Why |
|---|---|---|
| `PlanRepository`/`TaskRepository` return bare values | `AppResult<…>` | The gateway's refusals are part of the answer, and the four states of design review §12 have to stay distinguishable to the screen. A bare value would collapse them. |
| `GetStatusUseCase` returns `String` | `AppResult<PlanStatus>` | A prose summary would force the UI to parse text to learn whether the engine is halted. |
| `validate`/`renderIsCurrent` return `Boolean` | `PlanValidation` / `RenderCheck` | The contract's errors and issues are the point of the check. |
| `TaskBranch.guardsPassed: Boolean = false` | `Boolean? = null` | The console has not been told. `false` claims the gateway's verdict. |
| `TaskStatus` has three values | four, with `UNKNOWN` | An unrecognised status is not a licence to guess. |
| — | `PlanRepository.getStatus` added | The contract defines the route; the interface had no way to reach it. |

## Skipped Items and Rationale

- **The write layer** (`OperationRepository`, `OperationRepositoryImpl`, `domain/usecase/write/*`, `domain/usecase/common/*`, `domain/usecase/enrollment/*`) — not this stage. Those need a minted capability, and `OperationRequest` does not yet carry one; the write stage threads the `SignedCapability` through.
- **`TaskRepository.setStatus` is refused, not implemented.** The gateway contract defines no task-status route. A status change needs the gateway's plan store port — the compare-and-swap of docs/architecture.md §3 — which is the gateway's phase 3 and is not in the contract yet. The console refuses explicitly (`unsupported_operation`) rather than approximating a call to a route that does not exist or silently dropping the change.

  - `GatewayRepository.getPlan` (Stage 2.4) reports a plan that is not in the list as a *protocol* failure, which lands as `unknown` rather than `not_found`. The read layer therefore looks the plan up in the list itself, where the not-found semantics belong.
