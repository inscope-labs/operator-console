## 4. Ratchet Baseline Entries (Findings, NOT Approvals)

All 7 baseline entries below cause `ContractConformanceTest` to fail if removed while the underlying discrepancy still exists, or if any new discrepancy is introduced:

1. **`tasks_next:missing_work_order_id`** (`RESPONSE_RATCHET_BASELINE`, ref: `ADR 0014 D1`)
   - *Finding:* `tasks-next.schema.json` and `TaskSummaryDto` carry no work-order identifier in contract Revision 1.1; resolved via future contract Revision 1.2 + gateway update.
2. **`response_extra_field:enroll-rotate-response:enrolledAt`** (`RESPONSE_RATCHET_BASELINE`, ref: `PR3-003, contract §3.16, enroll-rotate.schema.json`)
   - *Finding:* `GatewayApi.rotateKey` reuses `EnrollResponseDto` (`enrolledAt`), a field absent from `enroll-rotate.schema.json` `definitions.response`.
3. **`response_missing_required:enroll-rotate-response:rotatedAt`** (`RESPONSE_RATCHET_BASELINE`, ref: `PR3-003, contract §3.16, enroll-rotate.schema.json`)
   - *Finding:* `EnrollResponseDto` omits `rotatedAt` required by `enroll-rotate.schema.json` `definitions.response`, so `RotateDeviceKeyUseCase`'s `response.enrolledAt > 0` check reads `0L` from real gateway responses and falls back to local device clock.
4. **`errormap_missing:IDEMPOTENCY_KEY_INVALID`** (`ERROR_CODE_RATCHET_BASELINE`, ref: `PR3-003, contract §4.1, BD-1.7`)
   - *Finding:* Revision 1.1 code missing from `ErrorMapper.GATEWAY_CODES` (`ErrorMapper` classifies it as `UNKNOWN`, whereas `OperationRepositoryImpl.KNOWN_GATEWAY_CODES` includes it).
5. **`errormap_missing:IDEMPOTENCY_KEY_REUSED`** (`ERROR_CODE_RATCHET_BASELINE`, ref: `PR3-003, contract §4.1, BD-1.7`)
   - *Finding:* Revision 1.1 code missing from `ErrorMapper.GATEWAY_CODES` (classified as `UNKNOWN` in `ErrorMapper`, though included in `OperationRepositoryImpl.CONFLICT_CODES`).
6. **`errormap_missing:OPERATION_NOT_FOUND`** (`ERROR_CODE_RATCHET_BASELINE`, ref: `PR3-003, contract §4.1, BD-1.7`)
   - *Finding:* Revision 1.1 code missing from `ErrorMapper.GATEWAY_CODES` (classified as `UNKNOWN` in `ErrorMapper`, though explicitly handled on 404 lookup in `OperationRepositoryImpl`).
7. **`errormap_extra:NOT_FOUND`** (`ERROR_CODE_RATCHET_BASELINE`, ref: `PR3-003, contract §4.1`)
   - *Finding:* `ErrorMapper.GATEWAY_NOT_FOUND` (`"NOT_FOUND"`) is absent from Contract §4.1 Error Code Registry (`BRANCH_MISSING` and `OPERATION_NOT_FOUND` are the §4.1 404 codes).

## 5. Operator Decisions Required / Flagged

1. **Strict vs. tolerant JSON decoding for gateway response bodies (`Task E(3)`):**
   - `GatewayRepository` (and `ErrorMapper` / `OperationRepositoryImpl`) currently configure `Json { ignoreUnknownKeys = true }` per contract §1.5 extensibility, silently ignoring unexpected response fields. Additionally, DTOs provide default property values so missing non-critical fields read as defaults rather than throwing.
   - Explicit test `E3_OPERATOR_DECISION_CURRENT_BEHAVIOR_GatewayRepository_tolerates_unknown_response_fields` pins this tolerant behavior; moving to strict (`ignoreUnknownKeys = false`) will intentionally break that test and requires a deliberate operator decision.
2. **Client-only gateway routes (`Task D`):**
   - `GatewayEndpoints.DECISION` (`"/decisions/{decisionId}"`) was the sole client-only gateway route and was **deleted** because it had zero callers. **Zero** client-only routes remain in `GatewayEndpoints`.
3. **`POST /enroll/rotate` response DTO (`§3.16`):**
   - Operator/remediation follow-up should split `RotateKeyResponseDto(kid, status, rotatedAt, authTier)` from `EnrollResponseDto` so `rotatedAt` is consumed instead of defaulting `enrolledAt = 0L`.
4. **`ErrorMapper.GATEWAY_CODES` Revision 1.1 parity (`§4.1`):**
   - Add `IDEMPOTENCY_KEY_INVALID` (`FORMAT`), `IDEMPOTENCY_KEY_REUSED` (`CONFLICT`), and `OPERATION_NOT_FOUND` (`NOT_FOUND`) to `ErrorMapper`, and decide whether legacy `NOT_FOUND` can be retired.
5. **`decide` / `status-transition` live-check & lookup semantics (`Questions 2 & 3`):**
   - Because `DecideAckDto` (§3.18) carries no `headSha`, `OperationRepositoryImpl.decide` currently remains permanently `UncertainCompletion` on write acknowledgement (and `DecideFrameworkUseCase` still defaults `contractSchemaSettled = false` pre-D2). Meanwhile `OperationRepositoryImpl.setTaskStatus` only checks `GET /branches/{name}/head`, not authoritative task/plan status (`SetTaskStatusUseCase` performs post-success refresh only).
