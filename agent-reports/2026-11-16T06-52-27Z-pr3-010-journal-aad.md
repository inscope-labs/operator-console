## 3. What the implementation does

### 3.1 The binding

`JournalAssociatedData.forColumn(recordKey, column)` derives the GCM associated data as a canonical, length-prefixed encoding of:

```
domain tag || scheme tag || len(recordKey) || recordKey || len(columnName) || columnName
```

- The **record** is identified by its journal primary key (`idempotencyKey`), the only value that identifies the row the ciphertext belongs to.
- The **column** is identified by the Room column name, enumerated in `JournalColumn` so the name cannot be mistyped or drift.
- Length prefixing makes the encoding unambiguous: no `(record, column)` pair can be confused with another, so a ciphertext replayed into a different record or a different column fails the GCM tag check.
- The derivation is pure and deterministic, so it is identical on encryption and on decryption, including after a process restart.

### 3.2 The enforcement point

`JournalFieldCipher` now reads:

```kotlin
interface JournalFieldCipher {
    fun encrypt(plaintext: String, associatedData: ByteArray): String
    fun decrypt(ciphertext: String, associatedData: ByteArray): String
}
```

The associated-data parameter is deliberately **not optional**. A call site that omits it does not compile — this is what makes the binding total rather than a convention. Every call site in `app/src/main/kotlin` was updated: 9 in `OperationJournalCodec` and 10 in `OperationRepositoryImpl`.

### 3.3 The seam that makes it testable

The AES-GCM mechanics and the wire format were split out of `AndroidKeystoreJournalCipher` into `JournalGcm`. The Keystore-backed cipher now delegates to exactly those functions and supplies only the key. This lets the JVM tests exercise **the production code path** — the real format, the real `updateAAD` call, the real fail-closed error handling — with a JVM-generated AES key, rather than a parallel implementation that could drift.

The AndroidKeyStore key policy is unchanged: the provider still generates the IV (`setRandomizedEncryptionRequired(true)`), the caller still never supplies one, and the 12-byte IV is still asserted.

### 3.4 Format version

The encrypted-field wire format moves from `v1:` to `v2:`. A `v1:` field carries no associated data and therefore cannot be authenticated under this scheme; it is rejected with the diagnosable message *"Unsupported journal field format version"* rather than being silently accepted. The application is pre-release (v0.6.0 in development, no production data), so no live journal row is stranded by this. **This is recorded here so the operator can confirm it is acceptable.**

### 3.5 Fail-closed behaviour

| Condition | Result |
|---|---|
| Ciphertext moved to another column | `JournalCryptoException` — "Failed to decrypt journal field" |
| Ciphertext moved to another record | `JournalCryptoException` — "Failed to decrypt journal field" |
| Ciphertext tampered | `JournalCryptoException` — "Failed to decrypt journal field" |
| `v1:` legacy field | `JournalCryptoException` — "Unsupported journal field format version" |
| Truncated payload | `JournalCryptoException` — "Encrypted journal field payload is truncated" |
| Keystore key missing | `JournalCryptoException` — "Journal encryption key '<alias>' is missing" |

No error message contains plaintext. The repository's existing `decryptOrFailClosed` path turns any of these into the `RECOVERY_REQUIRED` journal state and the `OperationOutcome.RecoveryRequired` outcome, so a journal crypto failure still fails closed (I-08).

## 7. Blockers, contract ambiguities and required operator / Claude actions

1. **Gateway operation ID is not journalled as a distinct field** (PR3-010 acceptance criterion 2). The journal persists the client-generated `idempotencyKey`, which is also the identifier used for `GET /operations/{id}` (ADR 0013, BD-1.7). If the gateway ever returns an *operation identifier that differs from the client idempotency key*, the console would have nowhere to persist it, because `OperationJournalEntity` has no column for it. Adding a column would change the Room schema (version bump + migration) and touch `OperationJournalDatabase.kt`. **Not done here — out of the `[REG+]` scope, and the schema change is not mine to make silently. Operator decision required:** either confirm that the client idempotency key *is* the operation ID (no schema change needed), or authorise a separate schema-versioned PR.
2. **Encrypted-field format version `v1:` → `v2:`.** Pre-release application, no production data, so nothing is stranded. **Operator confirmation requested** that no migrated journal is expected. No migration script is provided because no schema change occurs.
3. **`gradle/libs.versions.toml` comment** still reads *"Journal encryption is Keystore-wrapped AES-GCM field encryption using javax.crypto and the AndroidKeyStore provider (platform APIs), so no additional dependency is declared for it."* That statement remains true, but it no longer mentions the associated-data binding. **This file is a protected path and was not edited.** If the operator wants the comment updated, it must go through a `[CLAUDE]` branch and pull request.
4. **Data-classification table** was not produced as a standalone artefact (§4.2). Available on request as a small table derived from `JournalColumn`, `OperationIntent.init` and `ArchitectureTest` Rules F1/F2.
5. **The register itself was not modified.** PR3-010's acceptance text already describes the associated-data requirement; no register revision is needed for this change.
