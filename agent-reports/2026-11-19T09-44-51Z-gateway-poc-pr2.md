## 1. What changed

`gateway/src/routes/plans.ts` registered `GET /plans/:id/status` only. The transition route was **absent**, so the console's `SET_IN_PROGRESS` call had nothing to talk to. It is now registered next to it:

```
POST /plans/:id/status   requiresOperatorToken: true, requiresCapability: true
```

The handler follows `routes/decisions.ts` for the idempotency gate, `gateCapability`, the adapter and the response shape. It changes **one task's status in the gateway's plan record** and **does not commit to the consumer repository**.

### 1.1 The check order

The order is the contract's own (§3.17: *"Checks, in this order after the idempotency record is created (§1.6)"*).

| # | Check | Refusal |
|---|---|---|
| 1 | `gateIdempotencyWrite(…, 'SET_IN_PROGRESS', …)` | `IDEMPOTENCY_KEY_INVALID` / `IDEMPOTENCY_KEY_REUSED` / `OPERATION_NOT_FOUND` (no record created) |
| 2 | body: unknown keys, missing keys, `targetStatus`, `expectedHead`, path-vs-body plan | `400 BAD_ENCODING` |
| 3 | `gateCapability` (as `decide` uses it: `expectedBranch: body.branch`, Model A allowed outside production) | the gate's own code |
| 4 | capability op | `400 BAD_ENCODING` (reserved `SET` / `SET_DONE`), `400 UNKNOWN_OP` (any other op) |
| 4b | capability plan/task vs body plan/task | `400 BAD_ENCODING` |
| 5 | capability branch vs request branch; the task's recorded branch (if any) | `403 BRANCH_MISMATCH` |
| 6 | live branch head (`consumer.getRef`) | `404 BRANCH_MISSING`; `409 HEAD_MOVED` |
| 7 | `isHalted` | `409 HALT_ACTIVE` |
| 8 | `getPlanRecord`; unknown plan or task | `400 BAD_ENCODING` (the message names it) |
| 8b | `putPlanRecord` with the record's etag as `if-match` | `409 RECONCILE_REQUIRED` on a CAS conflict — nothing changes |
| 9 | `emitAudit` → `auditRef` | — |

Every refusal after step 1 closes the operation record through `finishFromResponse`, so `GET /operations/:id` reports it (`status: "refused"`, `code: <the refusal code>`).

### 1.2 Request and response

**Request keys are exactly** `plan, task, branch, expectedHead, targetStatus, idempotencyKey, capability` (the schema's `additionalProperties: false`). An unknown key is `400 BAD_ENCODING`. All seven must be present and non-empty; `expectedHead` must match the schema's `^[0-9a-f]{40}$`.

**Response keys are exactly** `accepted, operation, plan, task, newStatus, headSha, auditRef`:

```json
{
  "accepted": true,
  "operation": "SET_IN_PROGRESS",
  "plan": "atlas",
  "task": "10008",
  "newStatus": "in_progress",
  "headSha": "9f2c1b7e4a5d6038c1b2a9e7d4f6081c3b5a7e9d",
  "auditRef": "audit-20261119-48213"
}
```

The operation record for the same key carries `operation: "SET_IN_PROGRESS"`, `status: "completed"`, `branch`, `headSha` and `auditRef` — the shape `operation-lookup.schema.json` requires for a completed record.

### 1.3 What the transition changes

The **task's** status becomes `in_progress` (`PlanTaskRecord.status`), inside the plan record; the plan's own `status` is untouched. The contract says the operation *"changes the status of one task recorded by the gateway"*, and `plan-status-transition.schema.json` lists the other `targetStatus` values (`draft`, `ready`, `completed`, `halted`, `archived`) as reserved.

The write is a compare-and-swap: the record read at step 5 supplies the etag, and `putPlanRecord` sends it as `if-match`. A record that changed underneath is refused `409 RECONCILE_REQUIRED` and **nothing is written**.

## 4. Deviations, judgement calls and open questions

### 4.1 The nonce is consumed before the operation check — kept, not refactored

The contract lists the nonce check **last** (§3.17: *"the capability nonce is single use (`NONCE_REPLAYED`)"*, after the head and halt checks). `gateCapability` verifies the signature and then **stores the nonce** before the handler can look at the operation, so a capability carrying a reserved or wrong op has already burned its nonce. The brief instructed: keep it, do not refactor it, record the difference. **Recorded here.** The consequence is narrow — a refused capability cannot be re-presented, so the console must mint a fresh one after any refusal.

### 4.2 The path id / body plan / capability plan+task disagreement — `BAD_ENCODING`

The contract does not name this case. The brief instructed `BAD_ENCODING`, and that is what the route answers (step 2 for the path-vs-body plan, step 4b for the capability-vs-body plan and task). **Flagged as a contract silence.** In practice the console never trips it: `OperationRepositoryImpl.requireCapabilityMatchesRequest` already refuses to send a capability whose op, branch, head, plan or task differs from the request.

### 4.3 No source-state rule — open question

There is **no** rule such as "only a `ready` task may be transitioned". The contract does not name one, so none was invented: a task in any recorded status is transitioned to `in_progress`. **Open question for the operator:** should the transition be limited to a source status (e.g. `ready`), and if so, which code should carry the refusal? `BAD_ENCODING` is the only format code the contract offers for this route, but a source-state rule is a *state* rule, and the catalogue has no state code for it.

### 4.4 No publish-grade guard runs at all

The brief requires that G5–G8 are not run. In fact **no** publish guard runs on this route, and the reason is structural rather than a choice: G5–G8 vet a *diff* (ancestry, non-empty delta, merge commits, denied paths) and this operation does not touch the consumer repository, so there is no diff to vet — running G6 alone would refuse every transition. The route performs the contract's own ordered checks instead: the branch scope (step 5), the exact head (step 6) and the halt (step 7) cover the ground G3/G4/G13/G14 would have covered, with the codes the contract names. G1 (private repo), G11 (secret in diff) and G15 (submission immutable) are publish-specific and have no counterpart here.

### 4.5 An unreadable body has no operation record

A body that is not valid JSON is refused `400 BAD_ENCODING` **before** step 1, because the idempotency key cannot be read out of it. No operation record can exist for such a request, so `GET /operations/:id` has nothing to report. Every refusal *after* step 1 is recorded. (`decide` answers `NETWORK` for an unparseable body; `BAD_ENCODING` is the code the brief names for "body invalid" and is semantically right for a client-side framing fault.)

### 4.6 `BRANCH_MISSING` vs `NETWORK` while reading the head

The brief says an absent branch is `BRANCH_MISSING`. The route answers `BRANCH_MISSING` only when the adapter reports the ref as absent (a 404 / `Not Found`), and `NETWORK` for any other upstream failure — the pattern `routes/sync.ts` already uses. A 500 from the platform must not be reported as "this branch does not exist".

### 4.7 A record with no revision is refused, not written

`PlanRecord.etag` is always present in practice (both the Durable Object and the memory fallback mint one on every write). If it were ever absent, the compare-and-swap could not be honoured, so the route refuses `409 RECONCILE_REQUIRED` rather than writing without one. Fail closed.

### 4.8 The audit record is emitted on success only

`emitAudit` is called on the accepted path (step 9), and its `auditRef` is the response's `auditRef` — the contract §3.17 names the audit only for the success body, and the house pattern (`decide`, `halt`) is the same. A refusal is recorded in the **operation** record (§3.19), not in the audit stream. **Open question:** should refusals also emit an audit record? The audit stream is the journal of what happened; today a refused transition leaves no journal entry.

### 4.9 One read of the plan record, not two

The record is read once, at step 5, because that is where the task's *recorded branch* is needed. The same read supplies the etag for the compare-and-swap at step 8. Two consequences, both intended:

- The unknown-plan and unknown-task refusals stay at step 8's position in the contract's order, even though the read that discovers them happens earlier.
- A change between the read and the write is caught by the CAS (`409 RECONCILE_REQUIRED`), which is exactly the race the contract describes.

### 4.10 `PUT /plans/:id` still bypasses the capability-gated transition — reported, not fixed

`PUT /plans/:id` is registered with `requiresOperatorToken: true` only. It accepts a whole `PlanRecord`, `tasks` included, so a caller with the operator bearer token can set a task's status to anything — including `in_progress` — without a capability, and therefore without the branch, head and halt checks this PR adds. The brief says to leave it (the local PoC harness seeds plans through it, ADR 0016 D-2) and to report whether it should be limited to `ENVIRONMENT=test`. **It should be.** The route is reachable in production, and it is the same class of hole as the reserved-`SET` defect the contract already closes: the operator token is a bearer credential that travels with every console request, so it is a far weaker authorisation than an operator-signed capability. Recommended: require the capability on `PUT /plans/:id` outside `ENVIRONMENT=test`, or restrict the route to the test environment entirely.

### 4.11 `GET /operations/:id` needed no work

It already exists with `404 OPERATION_NOT_FOUND` and tests, and this PR uses it to prove the outcome is recorded. Nothing was changed there.

## 5. Anything that would make a console-minted capability or request fail

Checked against the console's own code, since the point of this route is to unblock the PoC chain:

- **Request shape matches exactly.** `PlanStatusTransitionRequestDto` carries exactly `plan, task, branch, expectedHead, targetStatus, idempotencyKey, capability` — the schema's seven keys and nothing else, so the route's "unknown request key" refusal cannot fire on a real console request. The endpoint path is `/plans/{planId}/status` (`GatewayEndpoints.PLAN_STATUS`) ✓.
- **Response shape matches exactly.** `PlanStatusTransitionAckDto` carries exactly the seven response keys ✓.
- **The console's capability survives PR 1's stricter decoder.** `DeviceNonceSource` draws 16 random bytes and renders them as `%02x` → **32 lower-case hex characters**, which satisfies the `^[0-9a-f]{16,64}$` rule PR 1 introduced. `OperatorCapability` requires `HEAD_REGEX = ^[0-9a-f]{40}$` and `EXP_REGEX = ^[1-9][0-9]{0,18}$` (canonical positive decimal, `Long`-ranged) — the same shape the gateway now enforces. The console's `TASK_BRANCH_REGEX` is the gateway's task-branch regex, character for character. **PR 1 does not break the console's capabilities.**
- **The engine-branch rules are compatible.** The console's `isEngineBranch` (a safe ref name that is not a task branch, ADR 0005 D-T2) is a **subset** of the gateway codec's acceptance rule: every engine branch the console can mint is accepted by the gateway. Verified by comparing the two rules over a list of branch shapes — the only differences are two punctuation characters the console refuses and the gateway tolerates, and `task-*` (which the codec refuses separately, as `BRANCH_MISMATCH`).
- **The console cannot mint the reserved `SET` operation.** The console's `OperationType` enum has no `SET` member at all — only `SET_IN_PROGRESS` and `SET_DONE`. The gateway's reserved-op refusal (`400 BAD_ENCODING`) is therefore reachable only from a hand-crafted capability.
- **The console's `completed` transition will be refused.** `OperationRepositoryImpl.setTaskStatus` maps `"completed"` to `SET_DONE`, which this route refuses `400 BAD_ENCODING` — reserved in revision 1.3 (completing a task is deferred, ADR 0016). That is the contract's intent, not a defect, but the console still offers the transition, so an operator can reach a 400 through the UI. Worth a look on the console side (out of this brief's scope).

## 6. Open questions for the operator

1. **Source state** — should the transition be limited to a source status (`ready`?), and which code would carry that refusal? (§4.3)
2. **The disagreement case** — the contract does not name the path/body/capability disagreement; `BAD_ENCODING` was used as instructed. Confirm. (§4.2)
3. **Audit on refusal** — should a refused transition emit an audit record as well as an operation record? (§4.8)
4. **`PUT /plans/:id`** — should it be limited to `ENVIRONMENT=test`, or made capability-gated outside it? (§4.10)
5. **The plan record's own `status`** — the contract's transition table names the *task* status; the plan's `status` is left untouched. Is a plan-level status update expected as well (it is what `GET /plans/:id/status` returns)?
6. **`required` versus "not empty"** — the schema marks all seven request keys `required`; the route refuses a missing key and an empty string alike, with `BAD_ENCODING`. Confirm that an empty string should be refused the same way as a missing key.
